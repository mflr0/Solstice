# Refactor report

Tree: `feat/v1.0` at 516b5ea. Source: eight audits (api-issues, api-admin, rest, server-rest, front-core, front-admin, front-work, hygiene) and the list of open pull requests at the time of the audits. No code was changed to produce this report.

How to read it. Every number in this report is a measurement taken at 516b5ea and has an entry in the measurements table (`[M1]`, `[M2]`, ...) with the command that produced it. Paths and line numbers in the ledger come from the audits; the claims marked "checked" in the section on disagreements were re-read in the tree. Command lines are written from the repository root.

## 1. Architecture verdict

The shape is sound and the debt is local. The Go package graph is layered and has no cycle: the leaves (`auth`, `db`, `i18n`, `secret`, `settings`, `sqlq`, `web`) import no other Solstice package, `events`, `notify`, `webhook` and `live` sit above them, and nothing below `api` imports `api`. Each cross-cutting rule has one owner: access rules in `perm` (the Go predicate and the SQL filter side by side), messages in `i18n` (a completeness test makes an unused or missing key impossible), audit actions in `audit`, events in `events`. Requests never wait on SMTP or HTTP: a handler emits an event, one bus goroutine writes rows, three polling workers send, and the shutdown order in `cmd/solstice` matches the comments. The Jira REST layer does not fork the business rules: it calls the interface's handlers through `uiCall` [M4], which is why the two APIs cannot disagree on a write. The interface is layered the same way (`core` is pure TypeScript, `lib` imports `core`, `ui` imports both, nothing points up), and the rules it mirrors from the server (user name and project key patterns, setting bounds, permission names, JQL error codes, audit actions) agree today, two of them guarded by tests that read the Go source.

The one structural caveat is `internal/api`: it is a single package of [M1] with HTTP, rules and SQL together, no service layer, among the other internal packages [M2]. The audits agree that this is workable and that splitting it is not worth proposing. The cost shows up in three forms. First, the same small piece is re-implemented in several files (a project-administrator test, an issue-key pattern, a "name is taken" query, a hand-built audit entry, the unmarshalling of an optional body), and some copies have drifted. Second, a few functions carry most of the complexity (`applyUpdate`, `updateBoard`, `createIssue`, `translateField`, `translateCustom`, `updateWorkflow`, `saveCatalogueItem`) and are among the least covered, so they cannot be split before characterization tests exist. Third, file boundaries follow history: `activity.go` holds several subjects, the custom-field write path lives in `rest_write.go` although the interface calls it, and statuses are split over two admin files. Two seams are inverted inside the package: the CSV export is built on the REST rendering layer while REST writes call native handlers, and the single-issue read and the batch read load the same relations twice.

The importer is the one structural weak spot. Its steps are copied by hand [M9], the unit tests cover the parser only, and the end-to-end script is the sole proof; `cmd/solstice` has no test at all, and the issue generator in `jirafixture` needs a golden test before any change. The safety net is thin for the whole train: the integration tests [M3] skip without a database and CI does not set one (PR #106 changes this), and the interface has no component test [M8], so every row that moves markup or state out of a Svelte component is blocked until a DOM test environment is accepted as a dev dependency. That is a decision for the maintainers, listed in section 6.

The asynchronous path has one robustness gap: a panic is recovered in one place only [M6], so a panic in a worker loop ends the process. PR #67 already adds the recovery and is not repeated here. The remaining debt is housekeeping: dead code with proof, unused interface texts, comments that break the repository's own comment rule, and compatibility branches for an "older server" that cannot exist because the interface is embedded in the server binary.

What blocks the train is mostly timing, not design. There are [M7] open pull requests, and most of `internal/api`, all five interface catalogues and all five server catalogues are touched by at least one. The ledger therefore gives, for every row, the open pull requests on its files, and the tickets list them in `blockedBy`. Rows whose files no open pull request touches go first; rows that need a characterization test say so; file moves go last.

## 4. Ledger

One row per candidate after merging duplicates; the audit ids a row came from are at the end of its `what` cell. The order is the order of the train: infrastructure and hygiene, then behaviour-preserving refactors, then file moves, with the interface after the server. Statuses:

- Proposed: the scope has a test proof today and no open pull request touches the files in scope (a row may name files it leaves out for that reason).
- Blocked: named by what, an open pull request number or `characterization required` (a test of the current behaviour has to exist first, or the test that pins the old shape has to be replaced by a better one, or a decision has to be taken).
- Rejected: no real cost, or the cost is above the gain; one-line reason.
- Deliberate - do not fix: looks wrong, is right; why.

Class: `safe` means the existing tests pass unchanged; `blocked: no test` and `blocked: pins` are the audits' words for the two reasons a row cannot be called safe.

Coverage figures and complexity ranks in the `test proof` column are quoted from the audits' input files (`cover-func.txt` for unit and integration tests together, approximate, and `gocognit.txt`), taken at 516b5ea and not re-run for this report. Where an audit names a test, the name is the proof; where it names a percentage, treat it as a pointer to the function and not as a gate.

The `open PRs on the files` column is the audits' list for the files named in `evidence`. The pull requests in a Blocked status are computed from the files in the scope of each ticket against the list of open pull requests, so the two can differ: a ticket that adds a new test file or leaves a file out is blocked by fewer.

## 5. Ticket train

A blocked ledger row with no ticket (status `characterization required`, a pinning test, or a decision) gets its ticket after the test or the answer exists; the tickets that add the tests are in the train.

## 6. Questions for the maintainers

Nothing below was guessed. Each one blocks or shapes a row or a ticket.

1. Component tests. May the interface take `jsdom` or `happy-dom` (with `mount` from `svelte`) as a development dependency? Without it the rows that move markup or state out of a Svelte component stay blocked (R116 to R132). The ticket "Interface tests: decide on a DOM environment" carries the question.
2. Empty operands in the query language (D20 to D22). For `timespent > EMPTY` and `statusCategory = EMPTY`: a query error, or the `IS NULL` behaviour that dates already have? Should `customfield = EMPTY` mean "has no value", like the other field types?
3. Free-text search (D23, R56). `text ~` in JQL and the simple search clean the same string differently. Which rule wins for hyphens and for words under the length threshold?
4. Project keys (R11). Readers accept an underscore; creation and the rename in #105 do not. Should an imported key with an underscore be creatable and renamable?
5. Names (R10). Workflow, transition and status names are cut at the column width, while most other names are refused when too long; a sprint name is cut on create and refused on edit; a board name is cut. Which rule?
6. English data in the database. The default workflow name, the statuses of the project templates and the default sprint name are stored in English, while the default catalogues follow the instance language. Should they?
7. Webhook update. `PUT` checks the target address again, with a DNS lookup, even when it did not change, so a hook whose host now resolves to a refused address can be deleted but not disabled. Intended?
8. Catalogue ids. `nextCatalogID` and `createStatus` read `MAX(id)+1` and insert without a lock; two simultaneous requests can end in a duplicate-key 500. Not reproduced. Worth a lock?
9. Settings page (D36). Should "Restore the original value" be disabled while the form is dirty, or re-seed only its own field? Should the save bar also show after a save error (the mail and webhook pages do, the others do not)? Which of the three ways that secondary lists fail (toast, silent, silent but visible) is the rule? May the compact text areas change their line height to one value?
10. Sprints. Completing a sprint counts and offers the move of open issues without sub-tasks, while the server moves every issue that is not done, sub-tasks included. Which is intended? Should an affected-version note exist like the released-version note on fix versions?
11. Links. Removing a link takes one click while attachments, comments, work logs and the issue itself ask twice. Intended?
12. Former search syntax (R57). Do stored filters, board queries or subscriptions on a real instance still use it? Only data can tell.
13. Times in webhooks (R12). Webhook payloads format times as the value is held (UTC), REST uses the configured zone. Intended?
14. Command line (D29) and credential changes (D46). Which account rules does the command line apply, and which sessions and tokens does a credential change end on each path?
15. Migrations. `db.Migrate` takes no lock while the importer takes `GET_LOCK`. Is any supported deployment able to start two migrating processes?
16. Key precedence. If a former key of one project equals the current key of another, `projectByKey` picks one without a stated order while `findIssue` gives the current key precedence. Does #105 prevent the collision?
17. `relatedIssues` sorts sub-tasks with a comparator that is not a strict weak ordering for pairs that are not both sub-tasks. It gives the right order for the data the query produces; replace it with `ORDER BY` in the sub-task branch?
18. Texts kept in English on purpose. Link history lines ("This issue blocks ...") are English because Jira stores them so; the reset and invitation link lifetimes are constants and also words in the catalogues. Keep both?
19. Who sees an e-mail address. The person page returns it to any signed-in user (tested behaviour); #90 narrows it. Leave to #90?
20. Epic by name (R86). The server accepts an exact name, the icon a substring. Should the issue type payload carry a flag so the interface asks the server?
